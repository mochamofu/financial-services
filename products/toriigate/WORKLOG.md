## R2 — 内部レッドチーム評価＋誤検知試験
`bf80d39` (2026-07-19)

### やったこと
攻撃10種＋誤検知スイートをライブのゲートウェイに流して採点。
**「悪を止められるか」と「善を通せるか」を同じ土俵で測る**のが狙い。

### 結果・発見
| 攻撃 | 検知率 |
|---|---|
| 既知クローラー・なりすまし・UA偽装・プローブ・低速スクレイパー | **100%** |
| **完全ブラウザ偽装＋分散IP** | **0%** ← 原理的限界 |

誤検知（人間・Googlebot・AI検索）は **0%**。

- 🐛 **重要な発見**：資源を投じた偽装スクレイパーはヒューリスティックでは原理的に止まらない。これはToriiGate固有の欠陥ではなく、識別情報ベース検知すべてに共通
- 📌 **その穴が戦略の裏付けになった**：`/api` に **Web Bot Auth 検証を必須**にすると、同じ攻撃が **0% → 20/20 遮断（100%）** に反転。「全ての回避者を追う」のでなく「正規を暗号署名で許可し、それ以外にコストを課す」というモデルが数字で裏付けられた
- 🐛 **PoW難易度12は実測0.4ms＝スクレイパーにほぼ無償**だった → 16（約120ms）に引き上げ

## R3 — 独立AIによる敵対的コード監査
`a6c302d` (2026-07-19)

### やったこと
別コンテキストの独立AIエージェントに、検知ロジック・チャレンジ・署名検証・
プロキシを**敵対的視点で監査**させた（「作者に忖度せず穴を探せ」）。

### 結果・発見 — **Critical 2件を含む13件**
| ID | 内容 | 重大度 |
|---|---|---|
| **C-1** | ASGIがクライアント制御の `X-Real-IP` を無条件信頼 → **なりすまし基盤**（GPTBotの正規IPを騙れる） | **Critical** |
| **V-1** | 既知署名にもブラウザ型にも当てはまらないUAが **HUMAN扱いで素通り**（UAを `Acme/1.0` にするだけで全面回避） | **Critical** |
| **C-2** | pass cookieがブロックリスト・罠・レートより先に評価され全スキップ（一度チャレンジを解けば1時間なんでもできる） | High |
| C-3〜C-10, V-5, V-20 | 例外DoS・署名リプレイ・SSRF・ヘッダ注入・無認証管理画面 ほか | Medium〜High |

### 📌 判断・対応
13件すべて修正し、**回帰テストを追加**（49→57件）。
特にC-2の修正で `evaluate()` の判定順を再構成 — **罠判定をcookieより前に**。
この順序自体が防御になっている。

> ⚠️ **反省点**：この時点の検知性能の数字は「私が書いて私が採点した」自作自演だった。
> 別ベンダーのモデルによる検証が必要、と自己注記。（→ R9・R10で対処）

## R9 — ファジング・静的解析・多モデルレビュー手順
`bea8e6f` (2026-07-25)

### やったこと
R3の C-3（非数値入力で例外）が**一件のバグでなく欠陥の"種類"**だと考え、
攻撃者到達パーサー10種に対するファジングハーネスを作成。静的解析（bandit）も導入。

### 結果・発見 — **初回実行で実バグ検出**
- 🐛🐛 **FUZZ-1（High・未認証DoS）**：`hmac.compare_digest` は非ASCII文字列で `TypeError` を投げる。
  そして **`torii_pass` cookie は攻撃者が完全に制御できる**。
  → **不正なcookieを1つ送るだけで、全リクエストが通る経路でゲートウェイが例外を投げる**。
  `Gateway.evaluate` 経由で再現確認。署名比較をbytesにし fail-closed に修正
- 🐛 FUZZ-2：非dictのJSONログ行で `AttributeError`
- 🐛 横展開で発見：プロキシの `Content-Length` に非数値を入れてもハンドラスレッドで例外
- 🐛 **bandit指摘（実質的な問題）**：脅威フィード取得にURLスキーム検証が無く、平文HTTPや `file://` を許容。
  あのレンジは「誰を*検証済み*クローラーとみなすか」を決めるので、**改ざんされると攻撃者IPを正規レンジに注入できる**（C-10のサプライチェーン懸念が現実になる経路）→ HTTPS強制に
- テスト 78→**101件**（ファジング回帰＋スモークを追加）

### 📌 判断
**1件の指摘を「その1行の修正」で終わらせず、同じ種類の欠陥を機械的に探す仕組みに変える**と、
人間/モデルのレビューでは見つからない実バグが出る。これは今後も原則にする。

`df4311c` (2026-08-08)

### やったこと
「どう検証を進め、どう評価し、いつ次に進んでよいか」を決める。
指標を自動測定するスコアカードと、**事業ゲート表**（何が測れたら何をしてよいか）。

### 結果・発見
- **性能を初めて実測**：判定オーバーヘッド p50 0.027ms / p95 0.047ms / p99 0.073ms、
  単一プロセスで約 32,000 req/s（判定のみ）
- ⚠️ **自分の測定設計ミスを発見**：既知型検知が88.9%でブロッカー判定になった。
  原因は `perplexity_stealth` を「既知型」に分類していたこと。
  このシナリオの**9リクエスト中8件はブラウザ完全偽装＋IP切替**＝機構的には高度偽装と同一。
  分類を機構ベースに訂正し、シナリオ単純平均→**リクエスト数で重み付け**にも修正
  → 正しい姿：**既知型100% / 高度偽装（ヒューリスティックのみ）2% / 同（署名必須時）100% / 誤検知0%**
- 📌 歯止めを明記：「指標が赤いときまず疑うのは指標の設計。**ただし緑にするための操作は厳禁**、機構で説明できる訂正のみ許す」

### 📌 事業ゲート表を定義
| ゲート | やってよくなること | 現状 |
|---|---|---|
| G1 | 無料ログ診断の提供 | ✅ **解禁済み** |
| G2 | monitorモードを顧客本番に設置 | L1・L2の実行待ち |
| G3 | enforce有効化（実際に遮断） | 実トラフィック計測が必要 |
| G4 | **有料で課金する** | 負荷試験・SLA・体制が必要 |
| G5 | 中堅・大企業に売る | ペンテスト・ISMS が必要 |

**合成テストが全部緑でも、解禁されるのはG1まで。**

## R11 — 修正の独立検証（L1）
`（このコミット）`

### やったこと
R3〜R9で入れた16件の修正を、**修正した本人とは別の検証者に確認させた**。
これが最大の検証空白だった（指摘は独立していたが、**修正は誰も検証していなかった**）。

### 結果 — **私の修正の多くが不完全だった**

| 判定 | 件数 |
|---|---|
| 適切に修正済み | 4件（V-20, C-3, FUZZ-1, BANDIT） |
| **不完全（回避経路あり）** | **8件** |
| **修正が新たな問題を導入** | **2件** |
| **新規発見** | **15件（N-1〜N-15）** |

### 🐛 特に痛かった3つ

1. **N-3（High）**：`verify_key` を持たないオペレーター（YouBot, DuckDuckBot,
   Claude-User 等）は **UA文字列だけで信用**されていた。`User-Agent: YouBot/1.0`
   の1本で無条件ALLOW。**製品の中核主張「UAは偽装できるからIPで検証する」が、
   レンジ未公開オペレーターのぶんだけ丸ごと機能していなかった。**
   PoWもブラウザ偽装も不要、ヘッダ1本で全部迂回できた。

2. ⚠️ **N-2（High）**：管理トークンの比較に、**R9で直したばかりの FUZZ-1 と
   まったく同じ `compare_digest` の欠陥**があった。つまり
   **自分が直したバグを、自分で別の場所に再導入していた**。
   → 対策として比較処理を共通ヘルパーに一本化（同じ過ちを繰り返せなくした）

3. ⚠️ **N-7（High）**：R3で入れた C-5（SSRF対策）が、**3xx/4xx/5xx の
   レスポンスヘッダを全消失**させていた。`Location` が消えるので
   **プロキシ配下のリダイレクト・ログインフローが全滅**する。
   セキュリティ修正が可用性を壊した典型例。

その他：pass cookieがカテゴリ判定を丸ごとスキップ（一度PoWを解けば1時間GPTBotを
名乗れる）、XFFのhopをIP検証しておらずブロックリスト回避可能、`0.0.0.0/0` が
CIDR検証を素通りして全IPが「検証済みGPTBot」になる、monitorモードが実際に429を返す…など。

### ⚠️ ファジング自体の欠陥も判明
harness が**パーサー単体しか対象にしていなかった**ため、
「パース結果が下流に流れる経路」（`handle_admin` 等）を見ておらず、
N-1・N-2・N-12 を2万反復でも検出できなかった。ターゲットを **10→13に拡張**。

### 📌 対応
16件を修正し、**回帰テストを47件追加**（101→**148件**）。
監査人が示した再現コードをすべて実行し、塞がったことを確認。
未対応の8件（N-4のO(n)劣化、C-4の再生防止、V-5のTTL設計など）は
設計変更が必要なため、重大度付きで [security-assessment.md](./docs/security-assessment.md) §3.7 に記録して次ラウンドへ。

### 📌 このラウンドの教訓
**「作った本人が直して本人が確認する」だけでは、Critical級の穴が残るどころか、
新しい穴を作ってすら気づかない。** 独立検証の価値がこのラウンドで実証された。
なお今回の検証者は同系統モデルなので、**別ベンダー（Codex/Z.ai）による検証は
まだ残っている**。

## この製品で守っている原則

1. **誤検知は検知率より重い** — 正規ユーザーやGooglebotを弾く事故は、ボット1匹通す損失より事業被害が大きい
2. **測れないものは「未検証」と書く** — 合成テストの緑で空白を隠さない
3. **「効いているように見えて素通り」は無防備より危険** — だから未検証のまま「防御できます」と売らない
4. **指摘は必ず回帰テストにする** — テストがなければ毎ラウンド同じバグを再発見して毎回払う
5. **自分の測定を疑う** — ただし数字を良くするための操作は厳禁

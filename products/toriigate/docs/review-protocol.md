# 多モデル検証プロトコル

セキュリティ製品を複数のAIモデルで検証するための手順と、そのまま貼れるプロンプト。

**設計原則**：モデルを並べるだけでは重複した指摘の山になる。効くのは
**①発見はブラインド並列（アンカリング防止）②役割を分ける ③修正を独立検証する
④確定した指摘を必ず回帰テストにする**の4点。

---

## 0. まず決定論的ゲートを通す（モデル不要）

```bash
cd gateway && ./quality.sh
```

テスト・ファジング・レッドチーム評価・静的解析を一括実行する。
**ここが赤いままモデルレビューに進まないこと** — 既知の不具合が指摘を埋め、
本質的な発見が埋もれる（トークンの浪費そのもの）。

| 段階 | 実行するもの | コスト |
|---|---|---|
| 毎コミット | `./quality.sh` | ほぼ無料・モデル不要 |
| 意味のある変更ごと | 敵役モデル **1体**（§2）を差分に | 小 |
| 節目のみ（パイロット前・enforce有効化前・リリース前） | 多モデル並列パネル（§2〜§4）＋ `FUZZ=200000` | 大 |

毎回フルパネルを回す必要はない。**節目だけで十分**。

## 1. 全体の流れ

```
[決定論的ゲート] ./quality.sh
        ↓
[発見] 敵役A・敵役B・敵役C を並列・ブラインドで実行
        ↓  互いの指摘は見せない（アンカリング防止）
[検証] 各指摘を別モデルが判定 → 過半が「本物」としたものだけ残す
        ↓
[修正] 修正＋回帰テストを書く（テスト無しの修正は再発する）
        ↓
[修正の独立検証] 修正した本人以外のモデルが「穴は閉じたか／新しい穴は無いか」
        ↓
[再ゲート] ./quality.sh を再実行
```

**発見は並列、順序が意味を持つのは修正→検証だけ。** 順番に回すと後続が
先行の指摘に引きずられ、独自の発見が減る。

## 2. 【発見】敵役プロンプト（各モデルに個別・ブラインドで投げる）

> 3体に**同じ**ものを投げる。互いの結果は絶対に見せない。

```
あなたは独立したセキュリティ・レッドチームのアナリストです。作者への忖度は不要、
攻撃者として容赦なく穴を探すのが仕事です。

【対象】
リポジトリ: https://github.com/mochamofu/financial-services
ブランチ: claude/ai-threat-security-software-t1ejgo
対象ディレクトリ: products/toriigate/gateway/toriigate/

【この製品は何か】
AIクローラー／AIエージェントのアクセスを検知・制御するゲートウェイ。
リバースプロキシまたはASGIミドルウェアとしてリクエスト経路に立ち、
クライアントを分類して allow / block / challenge(Proof-of-Work) /
throttle / tarpit / 402課金 のいずれかを適用する。

【脅威モデル（攻撃者の能力）】
- 攻撃者は任意のHTTPリクエスト（ヘッダ・パス・ボディ・Cookie）を無制限に送れる
- 攻撃者は複数IPを使える（IPローテーション可能）
- 攻撃者は本製品のソースコードを読んでいる（オープンな設計を前提とする）
- 攻撃者はゲートウェイの秘密鍵(TORII_SECRET)は持たない
- 攻撃者の目的は (a) 検知をすり抜ける (b) ゲートウェイを落とす/劣化させる
  (c) 正規ユーザーを誤遮断させる（サービス妨害）

【必ず評価すること】
1. 検知回避: この分類ロジックをすり抜ける具体的手法。実現容易度（高/中/低）付き
2. 判定順序の悪用: engine.py の evaluate() の評価順に、先に通る経路を悪用した
   バイパスは無いか
3. 例外・DoS: 攻撃者が制御できる入力で例外・無限ループ・メモリ枯渇を起こせないか
4. 暗号処理: challenge.py（HMAC・Proof-of-Work）と botauth.py（Ed25519署名検証）に
   検証不備・リプレイ・偽造の余地は無いか
5. プロキシ層: proxy.py にSSRF・ヘッダ注入・リクエストスマグリングの余地は無いか
6. 誤検知の誘発: 攻撃者が第三者の正規ユーザーを遮断対象に追い込めないか

【出力形式（厳守）】
指摘ごとに:
- ID・重大度（Critical/High/Medium/Low）
- file:line（必ず付ける）
- 悪用シナリオ（具体的な入力→結果。抽象的な懸念は書かない）
- 推奨する緩和策（1行）

【重要な指示】
- 確信が持てない指摘は「推測」と明記せよ。断定と推測を混ぜるな
- 「設計上意図的にそうしている」ものでも、攻撃者にとっての実際的な弱さは
  弱さとして評価せよ
- 既知の限界（完全なブラウザ偽装＋分散IPは検知できない）は既に文書化済み。
  それの再指摘ではなく、それ以外を探せ
- 前置き・要約・励ましは不要。指摘だけを出せ
```

## 3. 【検証】判定役プロンプト（各指摘に対し、発見者と別のモデルで）

> AIレビュー最大の失敗は「もっともらしいが間違った指摘」。ここで潰す。

```
あなたは懐疑的なセキュリティ検証者です。以下の指摘が**本物かどうか**を
コードを実際に読んで判定してください。あなたの仕事は指摘を反証することです。

【対象コード】
（リポジトリ・ブランチは上記と同じ）

【検証する指摘】
（敵役の出力をここに貼る — 1件ずつ）

【判定手順】
1. 該当箇所のコードを実際に読む
2. その悪用シナリオが**本当に到達可能か**を確認する（呼び出し元を辿る。
   途中に検証・早期returnが無いか）
3. 可能なら最小の再現コードを書いて確かめる

【出力】
- 判定: CONFIRMED（本物） / REFUTED（誤り） / UNCERTAIN
- 根拠: どのコードのどの行がそう言えるか
- REFUTED の場合: なぜ到達不能／既に対策済みなのか

【重要】確信が持てなければ REFUTED を既定とせよ。
偽の指摘を通すコストは、見逃しのコストより高い（開発リソースを無駄に消費する）。
```

**採用ルール**：3体中**過半が CONFIRMED** としたものだけを修正対象にする。

## 4. 【修正の独立検証】いま最も価値が高いパス

**背景**：独立監査で出た13件の指摘（Critical 2件を含む）は、
**指摘したのとは別のモデルが修正し、その修正を誰も独立に検証していない**。
ここが現時点で最大の検証空白。

```
あなたは独立したセキュリティ検証者です。過去に指摘された脆弱性に対する
「修正」が、本当に問題を解決しているかを検証してください。
修正した本人ではないあなたの目で、修正の不備を探すのが仕事です。

【対象】
リポジトリ: https://github.com/mochamofu/financial-services
ブランチ: claude/ai-threat-security-software-t1ejgo
対象: products/toriigate/gateway/toriigate/
修正内容の一覧: products/toriigate/docs/security-assessment.md の §3

【検証する修正（各項目について3点を判定）】
C-1  ASGIがクライアント制御のX-Real-IPを信頼 → trusted_proxies を導入
     （core.py resolve_client_ip / asgi.py）
V-1  未知の非ブラウザUAがHUMAN扱い → UNKNOWN_BOT に分類（scoring.py）
C-2  pass cookieがブロック/罠/レートを全スキップ → 判定順を再構成（engine.py evaluate）
V-5  PoW既定難易度12が無償 → 16に引き上げ（policy.py）
C-3  botauthの非数値createdで例外 → try で fail-closed（botauth.py）
C-4  botauthにメソッド束縛が無くリプレイ可 → @method を署名対象に追加（botauth.py）
C-5  proxyがoriginのリダイレクトを追従(SSRF) → 追従を無効化（proxy.py）
C-6  クライアント送出のXFF/カテゴリヘッダがoriginへ混入 → 転送前に除去（proxy.py）
C-7  管理エンドポイントが無認証 → admin_token で保護（engine.py）
C-8  body無制限 → 上限10MB（proxy.py）
C-9  TORII_SECRET未設定時に無言でランダム鍵 → 警告を追加（engine.py）
C-10 load_rangesがCIDR未検証 → 検証を追加（netranges.py）
V-20 検証済みエージェントがレート制限をスキップ → 適用（engine.py）

【各修正について判定すること】
1. 完全性: 元の攻撃は本当に成立しなくなったか。**回避する別経路は残っていないか**
2. 副作用: その修正が**新しい脆弱性や誤検知**を生んでいないか
3. 網羅性: 同じ種類の欠陥が**他の箇所にも残っていないか**（例: C-3と同じ
   「攻撃者制御の入力で例外」パターンが他のパーサーにも無いか）

【出力】
修正ごとに:
- 判定: 適切に修正済み / 不完全（回避経路あり） / 新たな問題を導入 / 未対応
- 根拠: file:line と、不完全な場合は回避シナリオ
最後に「同種の欠陥が残っている箇所」のリストを付けること。

【重要】「修正されているように見える」ではなく、コードを追って到達可能性を
確認せよ。確信が持てない場合はそう明記せよ。
```

## 5. 【必須】確定した指摘は回帰テストにする

ここが**モデル代を回収する唯一の仕組み**。テストを書かないと毎サイクル
同じバグを再発見して毎回払うことになる。

- 確定 → 修正 → `tests/` に**その攻撃を再現するテスト**を追加
- 実例: `tests/test_fuzz_regressions.py`（ファジングで見つけた未認証DoS）、
  `tests/test_engine.py` の C-1/V-1/C-2 回帰
- 追加後に `./quality.sh` を再実行して緑を確認

## 6. モデル選択について

**原則は「系統を散らす」**。訓練データも推論の癖も違うモデルを混ぜると盲点が
非相関になる。同一モデルを2回使うより、別ベンダーを1回使うほうが価値が高い。

特に重要なのは**作者と検証者を分けること**。同じモデルが書いて同じモデルが
レビューすると、構造的なバイアスが残る（実際、本製品の初期評価は
「書いた本人が採点した」ため自作自演の疑いが残ると注記されている）。

## 7. これでも埋まらない空白（誤った自信を持たないために）

多モデルレビューが全部グリーンになっても、それは**販売可能な品質の証明ではない**。
モデルレビューが見つけるのは**コードの欠陥**であって、以下は分からない：

- **実トラフィックでの妥当性** — 検知の前提が実世界で通用するか（最大の空白）
- **本気の回避** — 資源を投じた分散ブラウザ偽装（既に検知率0%と判明済み）
- **負荷時の挙動** — 大規模トラフィックでの性能・安定性
- **第三者ペネトレーションテスト** — 実際の攻撃者視点での実地検証

これらを埋めるのは [../testkit/](../testkit/)（実機＋実AIエージェント）、
実顧客のmonitorモード運用、負荷試験、外部監査。
詳細は [product-roadmap.md](./product-roadmap.md) と
[security-assessment.md](./security-assessment.md) を参照。

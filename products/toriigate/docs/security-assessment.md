# ToriiGate セキュリティ評価レポート

**対象**：ToriiGate ゲートウェイ MVP(`gateway/`)
**実施日**：2026-07-19
**手法**：敵対的レッドチーム(自動ハーネス＋独立AIによるコード監査)＋誤検知試験

> このレポートは「セキュリティ製品をどう品質確認すべきか」への回答でもある。
> 結論：**敵対的テスト(悪を止められるか)・誤検知試験(善を通せるか)・コード監査
> (製品自体が悪用されないか)を同じ土俵で回す**こと。片側だけでは意味を持たない
> (全遮断すれば検知率100%だが商品にならない)。

## 1. 評価の4層

| 層 | 問い | 手段 | 本評価での担保 |
|---|---|---|---|
| ① 機能正しさ | 各ルールが仕様通り発火するか | 単体テスト | `tests/` 57件パス |
| ② **敵対的/レッドチーム** | 攻撃者は検知を回避できるか | `redteam/` ハーネス | §2 |
| ③ **誤検知** | 正規ユーザー/Botを誤遮断しないか | `redteam/legit.py` | §2 |

再現：`cd gateway && python3 -m pytest -q && python3 -m redteam.run_assessment --pow`

## 2. 敵対的テスト＋誤検知の実測(層②③)

10種の回避手法をライブのゲートウェイに流し、検知率(悪を止めた割合)と誤検知率
(正規を止めた割合)を採点した。**「検知」= allow/log_only 以外のアクション**
(block・challenge・throttle・tarpit・monetize はいずれもクライアントにコストを課す)。

### 検知率(修正後)

| シナリオ | 件数 | 検知率 | 主なアクション |
|---|---|---|---|
| 正直な学習クローラー(GPTBot) | 8 | **100%** | block |
| なりすまし(GPTBot詐称・IP不一致) | 8 | **100%** | block |
| ブラウザUA詐称・ヘッダ欠落 | 8 | **100%** | challenge |
| 未知の非ブラウザUA(独自ツール) | 8 | **100%** | challenge |
| UAローテーション(ツール系混在) | 8 | **100%** | challenge |
| 脆弱性プローブ/ハニーポット踏み | 6 | **100%** | block |
| 低速スクレイパー(ツールUA) | 5 | **100%** | challenge |
| Perplexity型ステルス切替 | 9 | **11%** | 宣言相のみ捕捉 |
| **完全ブラウザ偽装(単一IP)** | 8 | **0%** | allow |
| **分散ブラウザ偽装(IP毎回変更)** | 40 | **0%** | allow |
| **トラップ回避型(ブラウザ偽装)** | 8 | **0%** | allow |

### 誤検知(False Positive)

| 正規トラフィック | 件数 | 誤検知率 |
|---|---|---|
| 本物の人間(デスクトップ/モバイル) | 12 | **0%** |
| Googlebot / Bingbot(正規レンジ) | 7 | **0%** |
| AI検索クローラー・AIユーザーエージェント | 4 | **0%** |

### この数字の読み方(最重要)

- **既知型・雑な攻撃には完璧(100%)、誤検知ゼロ。** ここは強い。
- **金をかけた「完全ブラウザ偽装＋IPローテーション」には無力(0%)。** これは
  ToriiGate固有の欠陥ではなく、**識別情報(UA・ヘッダ・IP)ベースのボット検知
  すべてに共通する原理的限界**。TLS/JA3・HTTP/2指紋・クライアントサイドJS・
  ML無しには、人間と区別できない。DataDomeやCloudflareでも同じ土俵では同じ穴を持つ。
- したがって**「ヒューリスティックで全部捕まえる」路線は行き止まり**。ここで
  事業計画の戦略が効いてくる(次項)。

### 穴を塞ぐ緩和レバー(実測)

| レバー | 分散ブラウザ偽装への効果 | 正規への副作用 |
|---|---|---|
| 既定ポリシー(ヒューリスティックのみ) | 0/40 遮断(素通り) | 誤検知0% |
| レート厳格化(max 8/10s) | 単一IPの高volumeのみ部分捕捉(4/12) | CGN/共有IPで誤検知リスク |
| **`/api` に Web Bot Auth 検証を要求** | **20/20 遮断**、署名済み正規は通過 | 誤検知0% |

→ **「全ての回避者を追う」のでなく「正規を暗号署名で許可し、それ以外にコストを課す」**
モデルが、ヒューリスティックを100%すり抜けた分散偽装を100%止めた。**事業計画の
中核戦略(Web Bot Auth前提の身元検証レイヤー)が、数字で裏付けられた。** 遮断技術の
コモディティ化に対し、これが持続的な差別化になる。

### Proof-of-Work のコスト(修正後)

| 難易度 | 反復回数(実測) | 解決時間 |
|---|---|---|
| 12(旧既定) | 約5千 | 約9ms |
| **16(新既定)** | 約6.9万 | 約120ms |
| 20 | 約36万〜 | 約0.6〜1.8秒 |

旧既定の12はスクレイパーにほぼ無償だった。16に引き上げ、フラグ済みクライアントに
1リクエストあたり約100msの実コストを課す(人間には不可視)。ただしPoWは**止める
のでなくコストを上げる設計**であり、単独の防壁ではない点は変わらない。

## 3. 独立コード監査の結果と対応(層④)

別個のAIエージェントに検知ロジック・チャレンジ・署名検証・プロキシ/ミドルウェアを
敵対的視点で監査させた。指摘は具体的で妥当なものが多く、**大半をその場で修正**した。

### 修正済み(このPRで対応)

| ID | 指摘 | 重大度 | 対応 |
|---|---|---|---|
| C-1 | ASGIがクライアント制御の `X-Real-IP` を無条件信頼→なりすまし基盤 | **Critical** | `trusted_proxies` を導入。信頼プロキシ経由の hop のみ採用、既定はソケットpeer(`core.resolve_client_ip`) |
| V-1 | 未知の非ブラウザUAが HUMAN 扱いで素通り | **Critical** | 既知署名でもブラウザ型でもないUAは UNKNOWN_BOT に(`scoring.py`) |
| C-2 | pass cookie がブロックリスト・罠・レートより先で全スキップ | **High** | 判定順を再構成。ブロック・罠を先に評価し、cookie保持者もレート制限対象に(`engine.evaluate`) |
| V-5 | PoW 既定難易度12がほぼ無償、docstringの「1秒」も誤り | **High** | 既定を16に、TTL/非ブラウザ解決の注意をdocstring修正 |
| V-20 | 検証済みエージェントがレート制限を全スキップ | Medium | 検証済みにもレート上限を適用 |
| C-3 | botauth の非数値 `created` で未捕捉例外→DoS | Medium | パースを try で包み fail-closed |
| C-4 | botauth に HTTPメソッド束縛・未来日付拒否が無くリプレイ可 | Medium | 署名対象に `@method` を追加、未来日付を拒否 |
| C-5 | proxy が origin のリダイレクトを追従→SSRF | Medium | リダイレクト追従を無効化(`_NoRedirect`) |
| C-6 | proxy でクライアント送出の XFF/カテゴリヘッダが origin へ混入 | Medium | 転送前にgateway管理ヘッダを除去(`STRIP_FROM_CLIENT`) |
| C-7 | 管理エンドポイント(/stats, /dashboard)が無認証 | Medium | `admin_token` 設定時は認証必須に |
| C-8 | リクエスト/応答 body サイズ無制限→メモリ枯渇 | Medium | 上限(既定10MB)を導入 |
| C-9 | `TORII_SECRET` 未設定時に silent なプロセス毎ランダム秘密 | Medium | フォールバック時に警告を発出 |
| C-10 | `load_ranges` が CIDR 未検証で敵対的フィードにより汚染/クラッシュ | Medium/High | CIDR検証・不正エントリskip・全滅時は例外 |

### 残存リスク(意図的トレードオフ／運用要件として文書化)

| ID | 内容 | 方針 |
|---|---|---|
| V-2 | 完全ブラウザ偽装＋分散はヒューリスティックでは原理的に検知不能 | Web Bot Auth 前提の許可モデルで対処(§2で実証)。将来的にTLS/JA4指紋を追加 |
| V-3 | verify_key の無い許可AI(Claude-User等)のUAは偽装可能 | ユーザー代理トラフィックは事業上通したい。厳格運用は `/api` 等で Web Bot Auth 必須ポリシーを使う |
| V-4 | IPローテーション自体はレート/評価を回避 | 上流の trusted_proxy 設定で X-Real-IP 偽装は封殺済み。IP評価単独に依存しない設計 |
| V-6 | ハニーポットが静的2パスかつ robots.txt で露出 | テナント毎の動的トラップ生成をロードマップに |
| V-7 | レスポンスの分類ヘッダが回避チューニングのオラクルになり得る | デバッグ用途。将来オプトイン化 |
| F-1 | シードIPレンジが狭く古く、実運用では正規Botを誤SPOOFし得る | **運用必須要件**：`netranges.load_ranges` で各社公開フィードを日次更新すること。シードは明示的にスナップショット |
| F-2〜F-4 | CGN/共有IP巻き込み、ヘッダ少なめ正規クライアント、モバイルIP変動でのcookieループ | ポリシーのレート閾値・許可パス・TTLで調整。既定は誤検知0%だが実トラフィックで要チューニング |

補足：C-4 は `@method` 束縛と未来日付拒否で改善したが、`max_age`(既定300秒)窓内の
同一メソッド・同一URLリプレイは依然可能。完全な単回使用(nonce台帳)は今後の課題。

## 3.5. ファジングで追加検出（decisive: 未認証DoS）

監査の C-3（非数値 `created` で例外）は**一件のバグではなく欠陥の"種類"**だった。
そこで攻撃者到達パーサーに対するファジングハーネス（`redteam/fuzz.py`）を作り、
「hostile input で例外を投げない」という不変条件を検証したところ、**即座に2件検出**した。

| ID | 内容 | 重大度 | 対応 |
|---|---|---|---|
| FUZZ-1 | `hmac.compare_digest` が非ASCII文字列で `TypeError`。**`torii_pass` cookie は完全に攻撃者制御**のため、不正なcookieを送るだけで全リクエスト経路で例外＝**未認証DoS** | **High** | 署名比較をbytesに変更し、判定全体を fail-closed に（`challenge.py`） |
| FUZZ-2 | JSONログ行がdict以外（配列・文字列・数値）だと `AttributeError` | Low | `isinstance` 検証を追加（`logscan.py`） |

同種の「攻撃者制御入力で例外」パターンを横展開で探し、
プロキシの `Content-Length` 非数値でも例外になる箇所を発見・修正した。

現在は10ターゲット × 20,000反復で**全て fail-closed**。この不変条件は
`tests/test_fuzz_regressions.py` に回帰テスト化済み（再発しない）。

**教訓**：1件の指摘を「その1行の修正」で終わらせず、**同じ種類の欠陥を機械的に
探す仕組みに変える**と、人間/モデルのレビューでは見つからない実バグが出てくる。

## 3.6. 静的解析

`bandit` を導入し8件の指摘を精査。1件は**実質的な問題**として修正した：
脅威フィード取得の `urlopen` にスキーム検証が無く、平文HTTPや `file://` を
許していた（**平文フィードを改ざんされると攻撃者IPを"検証済み"レンジに注入できる**
＝C-10のサプライチェーン懸念が現実になる経路）。HTTPS強制に修正。
残り7件は誤検知（未知IPのプレースホルダ文字列、cookie名、ゲートウェイの意図的な
全インタフェース待受）で、理由を明記して抑制。現在の指摘は0件。

## 4. 総括

- **今できること(強み)**：既知のAIクローラー・なりすまし・雑なスクレイパー・
  脆弱性プローブを、**誤検知ゼロで確実に捕捉**。中小〜中堅のWeb/APIを守る一次防壁
  として十分機能する。
- **原理的な限界**：資源を投じた分散ブラウザ偽装は、識別情報ベースでは止められない。
  これは全ボット検知製品に共通。**ToriiGateの答えは「身元検証(Web Bot Auth)で
  正規を許可し、それ以外にコストを課す」**であり、実測でその有効性(分散偽装
  0%→100%遮断)を確認した。市場が「遮断→選別・課金」へ動く中で、これが持続的な
  差別化になる。
- **プロセスとしての価値**：独立AIによる敵対的コード監査は Critical 2件を含む多数の
  実バグを検出し、その大半を即修正できた。**「別のAIに攻撃させて評価する」という
  アプローチは、セキュリティ製品の品質確認として極めて有効**であることが、この
  評価自体で実証された。継続的に(CI/定期で)回すべき。

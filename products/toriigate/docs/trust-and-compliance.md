# ToriiGate 信頼・コンプライアンス資料パック

セキュリティ製品は「トラフィックを覗く」ため、**買い手の信頼が導入の前提条件**。
このパックは (1) データ取扱いの明示、(2) コンプライアンス整備状況の正直な現在地、
(3) 代理店・情シスに配れるセキュリティ質問票の回答、(4) monitorパイロットの手引き
をまとめる。GTMの前提資産([gtm-japan.md](./gtm-japan.md) §7 で必須と整理)。

> 重要な前提：本製品は**プレGA(製品化前)**。本書は「現状の正直な開示」であり、
> 認証取得済みを主張するものではない。認証・第三者監査は [product-roadmap.md](./product-roadmap.md)
> のP4で取得する。**未取得の項目を"取得済み"と偽って売らないこと。**

## 1. データ取扱い（何を見て・何を保存し・何を保存しないか）

| データ | 見るか | 保存するか | 備考 |
|---|---|---|---|
| クライアントIP | ○ | 揮発（レート窓・累犯記憶のみ、TTLで消える） | 恒久保存しない。Redis利用時も窓/TTL内 |
| User-Agent | ○ | 直近イベントログに最大200字（メモリ内・上限5000件のリングバッファ） | ダッシュボード表示用。恒久DBなし |
| リクエストパス | ○ | 同上（直近イベント） | クエリ文字列は判定に使うが保存最小化 |
| リクエストボディ | 原則見ない | 保存しない | プロキシは転送のみ（上限10MB） |
| Cookie等の認証情報 | pass cookieのみ検証 | 保存しない（HMAC自己完結、サーバ側セッションなし） | 署名検証だけ |
| 個人情報(PII) | 収集目的では扱わない | しない | IPは通信制御目的の一時利用 |

- **恒久的なトラフィックDBを持たない**（現状のMVP）。イベントは**メモリ内リングバッファ**、
  メトリクスは集計カウンタ、メータリングは件数のみ。
- 構造化ログ(`TORII_LOG=json`)を有効化した場合、**ログの保管・保護は導入企業の責任**
  （出力先は顧客のログ基盤）。ログにはIP/UA/パスが含まれる点を導入時に明示すること。
- SaaSコントロールプレーン(P1)を作る際は、テナント分離・保存期間・削除権・所在地を
  本表に追記し、DPA(データ処理契約)を用意する。

## 3. セキュリティ質問票の回答（代理店・情シス配布用の雛形）

日本の調達でよく問われる項目への、現状に即した回答。**現状ベースで正直に**記載。

| 質問 | 回答（現状） |
|---|---|
| 通信は暗号化されるか | ゲートウェイはTLS終端の背後に置く構成を推奨。プロキシ自体のTLSは前段(LB)で終端 |
| 保存データの暗号化 | 恒久保存データを持たない（§1）。Redis利用時は顧客管理のRedisで保護 |
| 認証・アクセス制御 | 管理エンドポイントは `admin_token` で保護可。RBAC等はP1で追加 |
| ログ・監査証跡 | 構造化ログ(JSON)を出力可。保管は顧客側 |
| 可用性・冗長化 | 水平スケール対応（Redis共有状態）。SLAはP4で定義 |
| インシデント対応 | 脆弱性開示ポリシーあり([SECURITY.md](../SECURITY.md))。24/365体制はP4 |
| データ所在地 | 導入企業の環境内で動作（オンプレ/顧客クラウド）。SaaS版の所在地はP1で定義 |
| 第三者認証 | 現状なし（§2の通り正直に開示）。ISMS取得を計画 |
| サブプロセッサ | コア機能は外部送信なし。脅威フィード更新時のみ各社公開フィードを取得 |
| 脆弱性管理 | 内部レッドチーム＋独立監査を実施。第三者ペンテストは計画中 |

## 4. monitorモード・パイロット手引き（デザインパートナー向け）

**enforceの前に必ずmonitorでシャドー運用**する。これが「誤認させて売る」事故を防ぐ。

1. **オフライン診断から入る**：まず顧客のアクセスログを `toriigate-logscan` で解析し、
   AIボット露出を可視化（デプロイ不要・防御を約束しない・ゼロリスク）。
2. **monitorモードで設置**：`mode: monitor` で本番に置き、**遮断せず記録だけ**。
   実トラフィックでの分類結果と、enforce時に何が起きるかを2〜4週間観測。
3. **誤検知率を実データで計測**：正規ユーザー/SEOクローラーが誤って"遮断対象"に
   入っていないかを確認。閾値・許可リスト・チャレンジ難易度を顧客トラフィックに合わせる。
4. **合意の上でenforceへ**：誤検知が許容範囲だと双方で確認してから `mode: enforce`。
   まずは限定パス（`/api/` 等）から段階適用。
5. **効果を数値で共有**：ダッシュボード/メトリクスで遮断数・削減できた無駄アクセスを提示。

**パイロットで約束してよいこと**：可視化・監視・観測。
**約束してはいけないこと**：「完全に防げる」（原理的限界を [security-assessment](./security-assessment.md) に明記）。

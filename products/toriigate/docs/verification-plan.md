# 検証計画と評価基準

**「どう検証を進め、どう評価して、いつ次に進んでよいか」**を決める文書。

セキュリティ製品の検証は、基準を決めずに始めると無限に続く。逆に基準が甘いと
「効いているように見えて実は素通り」という最悪の状態で出荷される。
そこで本書は **①検証の段階（はしご） ②評価の指標と閾値 ③各指標が解禁する事業判断**
を紐づけて定義する。

---

## 評価の3原則

**① 単一の数字で評価しない。** 「検知率95%」は無意味に近い。攻撃者の練度で層別し、
誤検知・堅牢性・性能と並べて初めて判断材料になる。特に**誤検知は検知率より重い**
（正規ユーザーやGooglebotを弾く事故は、ボットを1匹通す損失より事業被害が大きい）。

**② すべての指標は「どの事業判断を解禁するか」に紐づける。** 紐づけないと
検証が趣味になり、出口がなくなる（→ §4 事業ゲート表）。

**③ 測れないものは「未検証」と明示的に記録する。** 合成テストの緑で空白を
隠すことが、この製品でいちばんやってはいけないこと。

---

## 1. 検証のはしご（進め方）

下から順に上る。**下の段が緑でないまま上に行かない**（既知の不具合が指摘を埋め、
本質的な発見が埋もれる＝時間とトークンの浪費）。

| 段 | 何を検証するか | 手段 | 頻度 | 状態 |
|---|---|---|---|---|
| **L0** | コードの回帰・堅牢性・基礎性能 | `./quality.sh` + `redteam.scorecard` | 毎コミット | ✅ 構築済 |
| **L1** | 設計・実装の脆弱性（人/モデルの目） | [review-protocol.md](./review-protocol.md) 多モデル並列 | 節目 | ✅ 手順構築済 / **未実施** |
| **L2** | 実クライアント・実AIエージェントでの挙動 | [testkit](../testkit/) 実機3台＋Codex/Z.ai | パイロット前 | ✅ 道具構築済 / **未実施** |
| **L3** | **実トラフィックでの妥当性** | 顧客本番で `mode: monitor`（2〜4週） | パイロット | ⬜ 未着手（最大の空白） |
| **L4** | 負荷・連続稼働耐久 | 負荷試験・長時間稼働 | enforce前 | ⬜ 未着手 |
| **L5** | 第三者視点・組織的信頼 | ペネトレーションテスト・ISMS/SOC2 | 有料販売前 | ⬜ 未着手 |

**現在地**：L0 は緑。L1・L2 は道具が揃っているが**まだ実行していない**。L3以降は未着手。

## 2. 評価の実行（自動化済み）

```bash
cd gateway
./quality.sh                     # L0のゲート（テスト・ファジング・静的解析）
python3 -m redteam.scorecard     # 指標を閾値と突き合わせて判定
python3 -m redteam.scorecard --json > scorecard-$(date +%F).json  # 記録用
```

### L0 の指標と閾値（提案値。文脈に応じて調整すること）

| 指標 | 閾値 | 種別 | なぜこの閾値か |
|---|---|---|---|
| 誤検知率（正規トラフィック） | **0件** | ブロッカー | 1件でも正規ユーザー/SEOクローラーを弾けば事業被害。合成段階で妥協しない |
| 既知型・雑な攻撃の検知率 | **≥95%** | ブロッカー | 既知シグネチャで捕まらないなら製品の前提が崩れる |
| 高度偽装（**署名必須ポリシー適用時**） | **≥95%** | ブロッカー | 差別化の核。ここが効かないと戦略が成立しない |
| ファジングで漏れた例外 | **0件** | ブロッカー | 攻撃者制御の入力で落ちる＝防御装置が防御を止める |
| 判定オーバーヘッド p95 | **≤5ms** | 警告 | 経路に立つので遅延は直接の導入障壁 |

> **層別が重要**：「高度偽装（ヒューリスティックのみ）」は**約0%**で、これは
> 閾値を設けない**記録項目**。識別情報ベース検知の原理的限界であり、
> 署名検証で対処する前提だから。ここを混ぜて平均すると評価が嘘になる。

### 測定設計の注意（実際に踏んだ罠）

- **シナリオ単純平均ではなく、リクエスト数で重み付けする**。40リクエストの
  シナリオと5リクエストのシナリオを同じ重みで平均すると数字が歪む。
- **層は「名前」ではなく「回避機構」で分ける**。`perplexity_stealth` は
  9リクエスト中8件がブラウザ完全偽装＋IP切替なので、既知型ではなく高度偽装に属する。
  当初これを既知型に入れていたため既知型が88.9%と表示され、原因を追ったら
  分類の誤りだった。**指標が赤いとき、まず疑うのは指標の設計**。
  ただし「緑にするために分類を動かす」のは厳禁で、機構で説明できる訂正のみ許す。

## 3. L1（多モデルレビュー）の評価ルール

### 指摘の重大度マトリクス（到達性 × 影響）

| | 影響: バイパス/停止/大量誤遮断 | 影響: 部分的 | 影響: 理論的 |
|---|---|---|---|
| **未認証で到達可能** | **Critical** | **High** | Medium |
| 条件付きで到達 | High | Medium | Low |
| 到達困難 | Medium | Low | Low |

例：ファジングで見つけた「不正cookieで例外」は *未認証到達 × ゲートウェイ停止* → **High**。

### 採否と収束の判定

- **採用**：3体中**過半が CONFIRMED** としたものだけを修正対象にする
  （偽陽性を通すコストは見逃しより高い＝開発リソースの無駄）
- **ブロッカー規則**：**Critical/High が1件でも未対応なら次の段へ進まない**。
  Medium は「期限と担当を決めて受容」を明記すれば進んでよい
- **打ち切り（収束）基準**：**新規の Critical/High が2ラウンド連続でゼロ**なら、
  そのレベルは"枯れた"と判断して次の段へ。これが無いとレビューが無限に続く
- **修正のたびに回帰テストを書く**。これが唯一モデル代を回収する仕組み
  （テストがなければ毎ラウンド同じバグを再発見して毎回払う）

### レビュアー自体の評価（メタ評価）

各モデルの **CONFIRMED率**（指摘のうち本物だった割合）を記録する。
極端に低いモデルはプロンプトか使い方に問題がある。
**モデルを評価せずにモデルの出力を信じるのは、検証していないのと同じ。**

## 4. 事業ゲート表 ← 評価の目的はこれ

**「何を測れたら、何をしてよいか」**。評価は事業判断を解禁するために行う。

| ゲート | やってよくなること | 必要条件 |
|---|---|---|
| **G1** | **無料ログ診断を顧客に提供** | L0緑 ／ 「防御を約束しない」文言の確認。顧客環境に何も置かないのでリスク最小 |
| **G2** | **monitorモードを顧客本番に設置** | L0緑 ＋ **L1でCritical/High 0件** ＋ **L2実機テストで誤検知0** ＋ 判定p95が合意値以内 ＋ 撤去手順の用意 |
| **G3** | **enforce有効化（実際に遮断する）** | G2 ＋ **L3で2〜4週の実トラフィック計測**、誤検知が顧客と合意した閾値以内 ＋ ロールバック手順 ＋ 限定パスからの段階適用 |
| **G4** | **有料で課金する** | G3 ＋ L4負荷試験 ＋ SLA定義 ＋ インシデント対応体制 ＋ データ取扱い開示（[trust-and-compliance](./trust-and-compliance.md)） |
| **G5** | **中堅・大企業に売る** | G4 ＋ **L5第三者ペンテスト** ＋ ISMS（可能ならSOC2 Type II） ＋ 記入済みチェックシート |

**現在解禁されているのは G1 まで。** L1・L2 を実行すれば G2 に進める。

> この表の意味：**合成テストが全部緑でも、それで解禁されるのは G1 と（L1L2実行後に）G2 だけ**。
> 「防御できる製品」として課金する（G4）には、実トラフィックと負荷と第三者検証が必要。

## 5. L2（実AIエージェント）の評価方法

L2のC項（Codex/Z.ai）は**合否ではなく観察**が目的。観察を判断に変えるため、
4項目を記録して**エージェント台帳**を育てる。台帳そのものが製品資産（署名辞書）になる。

| 観察項目 | 記録すること | これが意味すること |
|---|---|---|
| 名乗り | UA文字列（正直か・独自か・偽装か） | 署名辞書に追加すべき対象 |
| 分類 | どのカテゴリに落ちたか | `human` に落ちたら**検知の穴**（要対応） |
| robots.txt | 尊重したか | 悪性度の判断材料 |
| チャレンジ | 突破したか（JS実行できるか） | 単純フェッチャーか、ヘッドレスブラウザか |

**評価指標**：`特徴を把握できた実エージェントの数`。
これが増えるほど署名辞書が強くなる = 検知精度が上がる。

## 6. 記録（ラウンド台帳）

**記録しないと収束しているか判断できない。** 各ラウンドで以下を残す。

```markdown
### 検証ラウンド N — YYYY-MM-DD
- 実施レベル: L0 / L1 / L2 …
- 使用モデル: （敵役3体、判定役、修正検証役）
- スコアカード: scorecard-YYYY-MM-DD.json
- 指摘: Critical n件 / High n件 / Medium n件（うちCONFIRMED n件・REFUTED n件）
- 各モデルのCONFIRMED率: A=xx% B=xx% C=xx%
- 修正: n件（回帰テスト n件追加）
- 受容したリスク: （Medium以下。期限と担当を明記）
- 判定: このレベルは「枯れた／継続」
- 解禁された事業ゲート: G_
```

### 実績（参考）

| ラウンド | 内容 | 結果 |
|---|---|---|
| R1 | 内部レッドチーム（合成トラフィック10種＋誤検知スイート） | 高度偽装0%という限界を特定、署名必須で100%に反転することを確認 |
| R2 | 独立AIによる敵対的コード監査 | **Critical 2件**含む13件を検出・修正、回帰テスト化 |
| R3 | ファジング（攻撃者到達パーサー10種） | **未認証DoS 1件（High）**＋2件を検出・修正 |
| R4 | 静的解析（bandit） | 脅威フィードのスキーマ未検証（C-10関連）を修正 |
| **R5(R11)** | **修正の独立検証** | **修正8件が不完全・2件が新問題を導入・新規15件**を検出。16件を修正、回帰47件追加。ファジングの対象漏れも判明し10→13ターゲットに拡張 |
| R6 | **別ベンダーモデルによる敵対的レビュー** | **未実施** ← 次にやること（§7-1） |

> R11 の収束判定：**新規 Critical/High が出続けている（8件）ため「枯れていない」**。
> §3の収束基準（2ラウンド連続でゼロ）を満たすまで、L1 を継続する。

## 7. 次の一手（優先順）

1. **L1を実行**：[review-protocol.md](./review-protocol.md) §4 の
   「修正の独立検証」プロンプトを別ベンダーのモデルに投げる。
   R2〜R4の修正は**指摘したモデルとは別のモデルが修正し、誰も検証していない**
   ため、ここが現時点で最大の検証空白
2. **L2を実行**：[testkit](../testkit/) で実機＋実AIエージェント。
   エージェント台帳の初期データを作る
3. **L1L2が緑になったら G2**：デザインパートナー1社にmonitorモードで設置
4. **L3の計測設計を先に決める**：顧客と「許容できる誤検知率」を数値で合意してから
   置く（後から決めると揉める）

> 本書の閾値は提案値。顧客・業種・トラフィック規模で調整すること。
> ただし**「誤検知0を目指す」「Critical/Highを残して進まない」「測れないものは
> 未検証と書く」**の3点は動かさないこと。
